# 混打與 Kanata 研究

已唯讀檢查使用者提供的 kanata.kbd，不複製私人檔案進 Git。F 層使用兩種輸出：kp0–kp9、kp+、kp-、kp*、kp/、kp.；其他括號及符號以 `(unicode u+XXXX)` 輸出。

一般數字鍵、數字鍵盤事件、Unicode 文字提交不是同一條路徑。InputMethodKit 若收到帶 numericPad 的按鍵，可沿用上游；若 Unicode 直接進入目標應用的文字服務，輸入法不一定收到事件，因此不能宣稱攔截或改寫。若收到 keyCode 0xFFFF 的無修飾文字事件，可建立精確且受限的 literal 路徑，仍須現場整合驗證。

不開發 Caps/Control/F18 重映射、Tap-Hold、系統快捷鍵、全域監聽，也不調整 Kanata 設定。待驗證矩陣包括空組字、未完成音節、完成中文、候選視窗及不同目標應用。

混打採可取消 ASCII 組字入口；中文鍵序列維持原規則。英文詞庫只是候選來源，不能用字母序列自動推斷英文意圖。

產品參考：https://zingime.com/，官網標示「中英混打，無須切換」。使用者確認以混打與智慧選字體驗為目標；此時尚未實機驗證 Zing，也不推測其內部演算法。第一版明確入口是安全基礎，不能宣稱已達到無感混打。
